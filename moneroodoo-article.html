No Custodian, No Trust Required

📦 payment_monero_rpc · 🏷️ Odoo 18 · ⛓️ Monero (XMR) · 🔍 Three-Pass Security Audit

Every mainstream crypto payment gateway asks a merchant to trust a third party: an API key, a hosted checkout page, a company that can freeze funds or leak an order history. The payment_monero_rpc module for Odoo takes the opposite approach — it speaks directly to a self-hosted Monero daemon and wallet over RPC, generates a fresh subaddress per order, and verifies payment on-chain without a single external party ever seeing a transaction. This is a full technical walkthrough of how it works, and the 164-issue, three-pass audit that hardened it.

The Problem

Crypto Checkout Usually Means Trusting Someone Else's Server

Most Monero payment integrations for e-commerce platforms fall into one of two categories. The first is a hosted gateway: the merchant's site redirects to a third-party checkout page, which holds the wallet keys, sets the price, and reports back "paid" or "not paid" via a webhook the merchant has to trust blindly. The second is a thin API wrapper around a commercial payment processor that happens to support XMR alongside a dozen other coins — convenient, but it reintroduces exactly the kind of custodial intermediary that Monero was built to avoid.

For a merchant who already runs Monero infrastructure — a monerod daemon and a monero-wallet-rpc instance — neither option makes sense. The wallet is right there. What's missing is the glue: something that can generate a unique receiving address per order, poll the chain for incoming transfers, apply a confirmation policy, and hand a definitive "paid" signal back to Odoo's sales and point-of-sale flows, without ever touching a third-party server.

🔑
The core design constraint

Every Monero amount that moves through this module touches only two systems the merchant already controls: their own Odoo database and their own Monero daemon/wallet RPC endpoints. No API key. No hosted checkout. No webhook from a company that could go offline, get subpoenaed, or simply decide to hold funds.

The Solution

payment_monero_rpc: A Self-Hosted Bridge Between Odoo and the Monero Network

payment_monero_rpc is the current, unified generation of a lineage of Monero addons for Odoo. Two earlier modules — monero-rpc-odoo (a payment.acquirer-based e-commerce integration for Odoo 14) and monero-rpc-odoo-pos (a companion point-of-sale payment method) — have been merged into a single application built against Odoo 18's newer payment.provider framework, following Odoo's own naming convention for payment modules. The result installs as one app, registers as Monero (RPC) in Odoo's payment provider list, and works across both the website checkout flow and the point-of-sale register.

Underneath the Odoo integration boilerplate, four architectural decisions do the real work:

🧩
Isolation

One Subaddress Per Order

Every order gets its own Monero subaddress via wallet.new_address(), so incoming transfers can be matched to a specific order without a shared payment ID — and without leaking that two orders came from the same wallet.

🔌
No Custodian

Direct Daemon & Wallet RPC

The module talks straight to monerod and monero-wallet-rpc using the monero Python library. There is no third-party checkout server anywhere in the payment path.

🧮
Precision

Decimal-Safe State Machine

Payments move through pending → partial → paid_unconfirmed → confirmed (or overpaid / expired / failed), with row locks preventing double-confirmation and terminal-state guards preventing regression.

🖋️
Verifiability

HMAC-Signed Payment Proofs

Every confirmed payment can generate a tamper-evident proof — a SHA-256 HMAC over the payment ID, amount received, and address — signed with a server-side key, for disputes or bookkeeping.

Technical Deep Dive

Two RPC Clients, One Model Layer

The module cleanly separates the two roles a Monero node plays. MoneroDaemon (models/monero_daemon.py) is a lightweight status model that periodically polls monerod for sync height, peer count, difficulty, and network type, and stores a rolling history of snapshots — this is what confirmation counts are calculated against, so it never has to make a live RPC call on every page load. PaymentProviderMonero (models/payment_provider.py) extends Odoo's built-in payment.provider model and owns the wallet-side connection: it builds a Wallet(JSONRPCWallet(...)) client from the configured RPC URL, generates subaddresses, fetches balances, and converts fiat order totals into XMR using a cached exchange rate.

payment_provider.py — creating a payment from a fiat order total Python
def _create_monero_from_fiat_payment(self, order_ref, amount, currency, order_id): rate = self.get_xmr_rate(order_currency) wallet = self._get_wallet_client() if self.use_subaddresses: label = f"Order_{order_ref}" subaddress = wallet.new_address(label=label) payment_values = { 'payment_id': str(subaddress[1]), # subaddress index 'address_seller': subaddress[0], 'is_subaddress': True, } # ... integrated-address fallback for legacy payment-ID mode omitted payment = self.env['monero.payment'].sudo().create({ **payment_values, 'amount': float(Decimal(str(amount)) / Decimal(str(rate))), 'exchange_rate': rate, 'state': 'pending', 'expiration': fields.Datetime.add(fields.Datetime.now(), hours=24), }) return payment

Note the Decimal(str(amount)) / Decimal(str(rate)) conversion — a deliberate choice to avoid the classic float-division bug where two innocuous-looking floating-point numbers silently produce a fiat-to-XMR conversion that's off by a fraction of a piconero. The same pattern appears everywhere money changes representation in this codebase: piconero conversion uses the integer constant 1_000_000_000_000 rather than the float literal 1e12, and the HMAC payment-proof signature normalises amounts through Decimal(...).normalize() before hashing, so the same payment never produces two different signatures depending on how Python happened to render a float that day.

Floats are for display. Decimals are for money. The moment an amount crosses from "what the user sees" to "what gets compared, hashed, or persisted," it has to become a Decimal — or the module is one rounding error away from a payment that's confirmed on-chain but rejected by the state machine.

— design principle, monero_payment.py
End-to-End Flow

From Checkout Click to Confirmed On-Chain Payment

check_payment_status() on monero.payment is the workhorse of the module — called from a cron job every few minutes, and on demand when a customer or cashier wants a live status check. Here's the full path a payment takes:

Payment Lifecycle — monero.payment state machine
1
Order placed → subaddress generated

A fresh subaddress (or, in legacy mode, an integrated address with a random payment ID) is created and validated against the configured network before the monero.payment record is written.

2
QR code and address rendered to the customer

A QR payload is computed via an ORM dependency chain and served from the database, not held in the HTTP session — closing a code-path where a QR image blob once lingered in session storage.

3
Wallet RPC polled for incoming transfers

wallet.incoming() is filtered by subaddress index at the RPC level where the library supports it, falling back to a Python-side filter by address only when it doesn't — avoiding an O(n) scan of the entire wallet history on every poll.

4
Row-locked, terminal-state-guarded update

A SELECT ... FOR UPDATE NOWAIT is taken on the payment row before any write, and any payment already in confirmed, expired, or failed returns immediately — so two concurrent cron workers can never double-confirm the same payment, and a confirmed payment can never regress to pending.

5
Confirmation threshold evaluated

Amount received and confirmation count (read from the cached monero.daemon height, not a fresh RPC call) are compared against the provider's configured threshold to resolve partial, paid_unconfirmed, confirmed, or overpaid.

6
Order confirmed, proof generated, single email sent

_payment_confirmed() writes the final state, links the matching payment.transaction by reference, confirms the sale order with send_email=False, and sends exactly one confirmation email from the payment record's own template — a deliberate fix for an earlier double-email bug.

🛡️
Access control on every step

The website controller validates every order lookup against a hmac.compare_digest-checked access token before it will create a payment, check status, or serve a QR code — closing what was originally a complete bypass where access_token was accepted as a parameter but never actually verified.

Point of Sale

The Same Wallet, at the Till

Because payment_monero_rpc depends on point_of_sale and pos_online_payment, the identical fiat-to-XMR conversion and subaddress logic used on the website checkout is reused inside the POS register. An OWL component, MoneroPaymentPopup, patches Odoo's PaymentScreen to detect a payment line whose method is named "Monero RPC," generate the subaddress, render a QR code in-register, and poll for confirmation — with a shorter default expiry window than the e-commerce flow, since a customer standing at a register isn't going to wait 24 hours.

payment_screen_monero.js — reactive status state, not prop mutation JavaScript
import { Component, Dialog, useState } from "@odoo/owl"; import { DateTime } from "luxon"; patch(PaymentScreen.prototype, { setup() { super.setup(); this.activeMoneroPayments = new Set(); // Reactive state object — not this.props mutation, which OWL forbids this.moneroState = useState({ paymentStatusClass: "info", statusIconClass: "fa-hourglass-half", confirmationCount: 0, }); }, });

This snippet reflects one of the more instructive bugs found during review: an earlier version of _getStatusConfig mutated this.props directly and called this.render() — an anti-pattern in Odoo's OWL framework that fights the reactivity system instead of using it. The fix replaces prop-mutation with a proper useState object, letting OWL's own reactivity re-render the popup when confirmation counts change.

Version Strategy

Why Odoo 18, and Not the Newer Odoo 19

The current rewrite of payment_monero_rpc was carried out against Odoo 18 — a version that was already a year old, and whose support window was well understood, at the time the module was upgraded to it in April 2025. Odoo 19 did not exist yet: it shipped later that year, unveiled at the Odoo Experience conference in Brussels on 18–20 September 2025 and generally released the following month, October 2025. Odoo follows a strict annual October release cadence and supports only its three most recent major versions at any given time — each version gets roughly three years of bug fixes and security patches from its release date before it falls out of support, which is exactly the pattern that took Odoo 15 (released November 2021) out of support in October 2024, the same month Odoo 18 launched.

That timeline matters for a decision the manifest file makes explicit. Inside __manifest__.py, the live "version" key is pinned to "18.0.0.0.3", while a commented-out line sits directly above it — #"version": "19.0.0.0.3", for v19 — alongside a second commented note explaining that the post_init_hook entry would need to be removed to run on v19. In other words, the v19 migration path is already scouted and partially prepared in the source; it just hasn't been thrown as the default switch yet.

🧪
Fact-check: is that caution justified?

Yes, at least as a near-term call. As of mid-2026, Odoo 19 is still inside its first year in the field, and public bug trackers and user forums reflect the rough edges typical of a first-year major release: reported post-upgrade regressions around phone-number fields, mail templates, outgoing email, and Peppol e-invoicing; a product-variant pricing bug where a selected variant's price fails to update on the e-commerce storefront; and a wider catalogue of reported defects spanning Accounting, Website performance, Inventory serial-number uniqueness, Sales quote responsiveness, POS receipt formatting, HR approval routing, Project Gantt interactions, Manufacturing timers, and CRM lead enrichment. None of this is unusual for a release still in its stabilisation period — third-party trackers following the pattern have pointed to Odoo 19 reaching a more settled "maturity point" only around the middle of 2026 — but it is a reasonable basis for a payment-processing module, where correctness bugs have direct financial consequences, to stay one version behind the bleeding edge.

This is not a claim that Odoo 18 is somehow exempt from the same dynamic — every major version ships its own first-year rough patches, and Odoo 18 was no exception when it was new. The difference is simply elapsed time: by the point this module targeted it, Odoo 18 had already absorbed roughly six months of stable-branch bug fixes, whereas Odoo 19 is still accumulating its own. Odoo 18 is not in any EOL emergency either — with the three most recent major versions (17, 18, and 19) all under active support as of mid-2026, and Odoo 18's own support window not expected to close until roughly 2027 when Odoo 21 ships, there was no support-driven urgency to jump straight to 19. The commented-out version line in the manifest is the honest version of that decision: the module is ready to move to 19 once its ecosystem — and the third-party Python and JavaScript dependencies this module leans on — have had a full year to settle, not because 18 was running out of runway.

Honest Assessment

What Was Fixed, and What Was Consciously Left Alone

Not every issue found in the audit was resolved by rewriting code. Four items were deliberately documented as accepted technical debt rather than fixed outright, because closing them properly would require a database migration or an infrastructure change outside the module's scope:

🔢
XMR amounts stored as fields.Float

Monero has 12 decimal places of precision; IEEE 754 doubles carry roughly 15–17 significant digits, which is sufficient for amounts under ~1000 XMR but not a permanent guarantee. All comparisons and signature generation already convert through Decimal; the stored field itself is flagged for a future migration to an Integer piconero column with a fields.Monetary display layer.

🔐
RPC and wallet passwords stored in plaintext

Odoo's password=True field option only masks the value in the UI — the database column itself is unencrypted, and the same credential is additionally duplicated into ir.config_parameter. Documented as medium risk (it requires database read access to exploit) with a recommended future migration to environment variables or a secrets manager.

🧭
Subaddress orphaning on a database rollback

If a subaddress is generated on the wallet but the subsequent Odoo transaction rolls back, the wallet has an address with no corresponding payment record. Low risk, but it requires a periodic wallet-reconciliation job to detect and re-associate orphaned addresses — noted as a recommended future addition rather than built now.

⏱️
Exchange rate cache is a single shared value

The 60-second CoinGecko rate cache lives in a single ir.config_parameter row, so under multi-worker load there's a brief window where two workers could compute slightly different fiat conversions. Documented as low risk; a future fix would move this to Redis or add pessimistic locking around the cache write.

This kind of explicit debt-tracking — rather than silence — is arguably the most valuable output of the audit. A merchant deploying this module can read the accepted-risk table and make an informed call about whether stagenet testing is sufficient, or whether the float-precision and plaintext-password items need to be closed before mainnet production use at scale.

Conclusion

What a Self-Custodied Payment Gateway Should Look Like

payment_monero_rpc answers a fairly narrow but important question: can an ERP accept a privacy-preserving cryptocurrency without introducing a new trusted third party into the payment path? The module's answer is yes — at the cost of the merchant running their own daemon and wallet RPC infrastructure, in exchange for never handing a payment processor visibility into order amounts, customer identities, or transaction timing.

What makes it worth studying beyond its feature list is the audit trail sitting alongside it. A three-pass, 164-issue review that starts at 3.0/5 and documents its way to 5.0/5 — with every fix traceable to a specific issue number, and every piece of remaining risk written down rather than hidden — is a more honest account of software quality than a green "production-ready" badge on a README.

Security work that isn't documented didn't happen, as far as the next reviewer is concerned. A fix without a paper trail is indistinguishable from a bug nobody noticed yet.

— audit methodology note
