Monero payments · Odoo 18, 19 and 20

No Custodian, No Trust Required

📦 payment_monero_rpc· 🏷️ Odoo 18 · 19 · 20· ⛓️ Monero (XMR)· 🔍 Static audit + runtime review

Every mainstream crypto payment gateway asks a merchant to trust a third party: an API key, a hosted checkout page, a company that can freeze funds or leak an order history. The payment_monero_rpc module for Odoo takes the opposite approach. It speaks directly to a self-hosted Monero daemon and wallet over RPC, generates a fresh subaddress per order, and verifies payment on-chain without an outside party ever seeing a transaction. The module now supports Odoo 18, 19 and 20, packaged as three independent directories. This article walks through how it works, how the three versions differ, and what two security reviews changed.

What changed

One Module, Now for Odoo 18, 19 and 20

Until this update the repository held a single Odoo 18 module at its root, with a commented-out 19.0 version string in the manifest. It now holds three complete modules, one per Odoo series, under addons/. Each has its own manifest, security files, tests and a ready-to-upload zip. The older Odoo 14 modules moved to legacy/.

The Problem

Crypto Checkout Usually Means Trusting Someone Else's Server

Most Monero integrations for e-commerce platforms are one of two things. The first is a hosted gateway: the shop redirects to a third-party checkout page that holds the keys, sets the price and reports "paid" through a webhook the merchant has to trust. The second is a thin wrapper around a commercial processor that supports XMR next to a dozen other coins, which brings back exactly the custodial intermediary Monero was built to avoid.

A merchant who already runs monerod and monero-wallet-rpc needs neither. What is missing is the glue: a unique receiving address per order, polling for incoming transfers, a confirmation policy, and a definitive "paid" signal back to Odoo's sales and point-of-sale flows.

🔑
The core design constraint

Every Monero amount that moves through this module touches only two systems the merchant already controls: their own Odoo database and their own Monero daemon and wallet RPC endpoints. No API key, no hosted checkout, no webhook from a company that could go offline or hold funds. The one outside call is the exchange-rate lookup (api.coingecko.com by default, with manual fallback rates configured on the provider), which carries a currency code and no order data.

The Solution

payment_monero_rpc: A Self-Hosted Bridge Between Odoo and the Monero Network

payment_monero_rpc is the current generation of a lineage of Monero addons for Odoo. Two earlier modules, monero-rpc-odoo (a payment.acquirer integration, version 14.0.1.0.2) and monero-rpc-odoo-pos (a point-of-sale companion), were merged into one application built on Odoo's payment.provider framework. It installs as one app, registers as a Monero (RPC) provider, and covers both website checkout and the POS register.

🧩
Isolation

One Subaddress Per Order

Each order gets its own subaddress from wallet.new_address(), so incoming transfers match a specific order without a shared payment ID, and two orders are not linkable to the same wallet by an observer.

🔌
No Custodian

Direct Daemon & Wallet RPC

The module talks to monerod and monero-wallet-rpc through the monero Python library. No third-party checkout server sits in the payment path.

🧮
Correctness

A Locked State Machine

Payments move through pending, partial, paid_unconfirmed and confirmed (or overpaid, expired, failed). Row locks prevent double confirmation and terminal states never regress.

🖋️
Records

HMAC-Signed Payment Proofs

A confirmed payment can produce a JSON proof whose HMAC-SHA256 signature the merchant can later re-check against their own key. It is tamper-evidence for the merchant's records.

Technical Deep Dive

Two RPC Clients, One Model Layer

The module separates the two roles a Monero node plays. MoneroDaemon (models/monero_daemon.py) is a status model, refreshed by cron every five minutes, that records monerod's height, connections, difficulty and network and keeps only the latest few snapshots. Confirmation counts read this cache instead of making a live RPC call on every page load. PaymentProviderMonero (models/payment_provider.py) extends payment.provider and owns the wallet side: it builds a Wallet(JSONRPCWallet(...)) client from the configured URL (scheme, host and port are all honoured, so an https:// URL stays TLS), generates subaddresses, and converts fiat totals to XMR.

payment_provider.py — creating a payment from a fiat order total (excerpt, comments shortened)Python
def _create_monero_from_fiat_payment(self, order_ref, amount, currency, order_id): self.ensure_one() order_currency = currency.name if hasattr(currency, 'name') else currency rate = self.get_xmr_rate(order_currency) if not rate: raise UserError(_("Could not get exchange rate for %s") % currency) wallet = self._get_wallet_client() if self.use_subaddresses: label = f"Order_{order_ref}" subaddress = wallet.new_address(label=label) if not self._validate_address(subaddress[0], is_subaddress=True): raise UserError(_("Generated invalid subaddress for current network")) payment_values = { # payment_id is left unset so create() fills it with secrets.token_hex(32) 'subaddress_index': subaddress[1], 'address_seller': subaddress[0], 'is_subaddress': True, } # ... integrated-address branch for legacy payment-ID mode omitted payment = self.env['monero.payment'].sudo().create({ **payment_values, 'amount': float(Decimal(str(amount)) / Decimal(str(rate))), 'exchange_rate': rate, 'currency': 'XMR', 'order_ref': order_ref, 'state': 'pending', 'expiration': fields.Datetime.add(fields.Datetime.now(), hours=24), 'original_amount': amount, 'original_currency': order_currency, }) return payment

Notice what the subaddress index is not used for. It goes into its own subaddress_index field, while the public lookup key payment_id is generated by monero.payment.create() as secrets.token_hex(32): 64 random hex characters. An earlier version stored the index itself as the payment_id, and because the status route looks payments up by that value, anyone could walk it by counting "1", "2", "3". Subaddress mode is the default, so that was the key every normal checkout received.

Money conversion goes through Decimal(str(amount)) / Decimal(str(rate)) so the division does not inherit float error, and the proof signature normalises the amount with Decimal(...).normalize() before hashing. The honest limit is storage: amounts are Odoo Float fields at 12 digits, and the model's own field help notes that sub-piconero rounding is possible and that integer piconeros would be the better representation. Received and expected amounts are compared with float_compare(..., precision_digits=12).

End-to-End Flow

From Checkout Click to Confirmed On-Chain Payment

check_payment_status() on monero.payment is the workhorse. A cron (_cron_verify_pending_payments) runs it every five minutes over up to 100 unexpired pending, partial and paid_unconfirmed payments, least recently checked first. The customer's payment page also polls the token-keyed status route. The path a payment takes:

Payment lifecycle — the monero.payment state machine
1
Order placed, subaddress generated

The /shop/payment/monero/process/<order_id> route requires the order's access token. If the order already has an active payment (pending, partial, paid_unconfirmed or overpaid) it is reused, so a refresh or double-click does not burn another subaddress; a cancelled order gets none. Otherwise a subaddress is created, validated against the provider's network type, and stored with a 24-hour expiry.

2
QR code and address rendered to the customer

The monero: payment URI (address, tx_amount, description) is computed on the record and encoded into a PNG by the qrcode library. It is read from the database, never cached in the HTTP session. The payment page and the QR image both require the order's access token; a tokenless request gets a 404.

3
Wallet RPC polled for incoming transfers

The code first asks for wallet.incoming(account=0, subaddr=N). The monero library rejects those keyword arguments with ValueError, so in practice every poll falls back to wallet.incoming() and filters by receiving address in Python. That is a full scan of the wallet's incoming history per payment, not an RPC-level filter; it is correct, and worth knowing when sizing a busy shop.

4
Row-locked, terminal-state-guarded update

A SELECT ... FOR UPDATE NOWAIT is taken on the payment row before any write, so two workers cannot both confirm the same payment. A payment already confirmed, expired or failed returns immediately. A transient RPC error records the message and timestamp but leaves an active payment where it is, so one bad poll cannot fail a good payment.

5
Transfers saved first, then the state is resolved

Transactions are upserted before the state is computed, keyed on (txid, payment_id). Each transaction's confirmations are the larger of the wallet-reported count and the count derived from the cached daemon height; the payment uses the smallest across its transactions and compares it with the provider threshold (at least 1 is enforced).

6
Order confirmed, one email sent

_payment_confirmed() writes the state, marks the matching payment.transaction done by reference, confirms the sale order with send_email=False, and sends one confirmation email from the payment's own template. Failures in the email or chatter post are caught and logged, so nothing after the state write can turn a paid order back into a failed payment.

🛡️
Access control on every route

Creating a payment, the payment page, the QR code, the invoice and the proof all require the order's access token, checked with hmac.compare_digest. The status poll is keyed by the 64-character payment_id and returns a generic message on error instead of internal RPC details. The bulk /verify route is restricted to users in the Monero groups, and the token-gated QR is served with Cache-Control: private. Funds that arrive after a payment has expired are not recorded; that guard is deliberate, so decide your expiry policy with it in mind.

Payment Proofs

What the HMAC Proof Does and Does Not Prove

For a confirmed payment, generate_payment_proof() writes a JSON attachment containing the payment ID, address, amount, confirmations, transaction hashes, the lowest block height and a signature. The signature is an HMAC-SHA256 over payment_id:amount_received:address keyed with monero.payment_proof_key, which the post-install hook generates once as secrets.token_hex(32) and stores in ir.config_parameter. Uninstalling the module keeps the key.

Because the key is symmetric and stays on the merchant's server, only the merchant can verify a proof. It shows that a record has not been altered since it was issued; a customer or third party cannot check it independently. The signature covers those three fields only, and the key is stored in plaintext in the database, so back it up: losing it makes old proofs unverifiable.

Point of Sale

The Same Wallet, at the Till

On the server side, models/pos_payment.py extends pos.payment.method with a linked provider, an is_monero flag and a QR size, and adds monero_payment_id, with its status and confirmation count, to pos.order. The payment itself is created by the same provider method as website checkout. These models install and pass their tests on all three series.

The 18.0 frontend overlay adds MoneroPaymentPopup, which extends core's OnlinePaymentPopup and shows the QR code, the XMR amount and a live status, and patches PaymentScreen to open it and poll the payment on a 60-second interval. The popup closes itself after a hard-coded 15-minute countdown. Status is held in reactive OWL state rather than by mutating props:

⚠️
The POS frontend has not been run in a browser

No POS session or browser test has been run on any series, so the POS overlay and the website checkout JavaScript are unverified. On 19.0 core moved online-payment validation to OrderPaymentValidation.isOrderValid, so this module's _isOrderValid override is not invoked there and must be retargeted. Packaging & Versions

One Module, Three Directories: Odoo 18, 19 and 20

The differences between series touch security groups, access rules, constraints, binary fields and the POS overlay. They are not worth hiding behind version checks, so each series is a readable module of its own, and the Python models are nearly identical: payment_provider.py and monero_daemon.py are the same on 18.0 and 19.0, and 19.0 to 20.0 differs by a few dozen lines. Version differences were checked against the real odoo/odoo sources of the three branches, and each series was installed and tested on a live Odoo and PostgreSQL.

Security Review

Static Passes First, Then the Runtime Review That Found What They Missed

The original review read the Odoo 18 code without running it: three passes found and fixed 164 issues (124, then 25, then 15), and its rating climbed from 3.0 to a final 5.0 out of 5. That report is preserved as monero_code_review_three_pass.md. The ratings are the static reviewer's; they were never a statement that the module had been run.

Then the module was installed on real Odoo and PostgreSQL and driven over real HTTP. That found defects no reading had caught, starting with the first install:

19 further findings, all fixed on every series

The runtime report, monero_code_review_final.md, lists 19. Fifteen came from the first real run; four surfaced only because fixing those exposed code that had never executed. They fall into a few groups:

Checkout could not work or could be abused. Guest checkout raised AccessError because payment.provider was read without sudo(), and behind that a QR image of raw bytes broke session serialization. The payment page had no access-token check. The process route created a new payment and subaddress on every retry and accepted cancelled orders. The token-gated QR was marked publicly cacheable, and internal RPC details were echoed to anonymous callers.

Payment state could be wrong. Confirmations depended entirely on the daemon cache, so an empty monero.daemon table stalled payments at paid_unconfirmed. One transaction paying two payments only attached to the first. A mail failure after confirmation could flip a paid payment to failed, and so could a single RPC timeout.

Configuration and access. The shipped provider was enabled with published credentials and a developer's home path. An https:// RPC URL was silently used over plain HTTP. Address validation ignored the network type, the confirmation threshold could be zero, two crons did the same job, a Monero Admin could edit every provider's credentials, and a Monero Manager could write any POS order.

🔎
The constraints that were never created

Re-running the suites on fresh installs found that on 19.0 and 20.0 the database had no UNIQUE(payment_id), no CHECK(amount > 0) and no UNIQUE(txid, payment_id). Odoo 19 and later ignore _sql_constraints, logging a warning and creating nothing. Every test passed anyway, because none asked the database. They are now models.Constraint attributes, checked against pg_constraint. 18.0 was unaffected.

The existing tests all passed regardless, because none of them asserted that a constraint exists.

TEST_RESULTS.md
Scope & Limits

What Was Fixed, and What Is Still Unverified

Two behaviours look like defects but are intended, and the runtime review now has tests asserting them: overpayments never auto-confirm, and funds arriving after a payment has expired are not recorded. Both are policy choices an administrator should know about.

⚠️
Known gaps

The 27 adversarial probes exist on 18.0 only; 19.0 and 20.0 run their shipped suites plus the constraint tests. No browser or POS session has been run, so the POS and checkout JavaScript are unverified on every series. Wallet and daemon calls are mocked in every test and nothing has talked to a real monerod or monero-wallet-rpc, so try stagenet before mainnet. Exchange-rate fetches were blocked in the test sandbox. The GET route /shop/payment/monero/transaction validates the order token but creates a new payment on every call, with no cancelled-order check and no reuse of an active payment, on all three series; only the JSON process route has those protections.

🧾
Accepted, documented debt

Amounts are stored as Float (12 digits, as described above); integer piconeros would be exact and need a migration. The RPC and wallet passwords are stored as plain text in the database, and password=True only masks them in the interface. A subaddress can be orphaned: the wallet issues it before the payment record is created, so a database rollback after that leaves an unused subaddress labelled Order_<ref> in the wallet. The exchange-rate cache is 60 seconds per currency in ir.config_parameter and is shared by all workers, so workers can briefly disagree.

Conclusion

What a Self-Custodied Payment Gateway Should Look Like

payment_monero_rpc answers a narrow question: can an ERP accept a privacy-preserving cryptocurrency without adding a trusted third party to the payment path? The answer is yes, at the cost of the merchant running their own daemon and wallet RPC, in exchange for never giving a processor visibility into order amounts, customers or timing. With this update that answer holds for three Odoo series, each installable on its own.

What makes it worth studying beyond the feature list is the record next to it. A static audit that rated the module 5.0 out of 5, followed by a runtime review that found 19 more defects and a constraint bug on the newer series, is a fair picture of what each kind of review can and cannot see, and the remaining risks are written down rather than hidden.

The module descends from the Monero Integrations project's monero-rpc-odoo and monero-rpc-odoo-pos addons for Odoo 14; this version unifies both into one app for Odoo 18, 19 and 20.
